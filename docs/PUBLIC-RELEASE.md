# Making the repository public

A checklist for the owner. Rev 0 is complete at 0.3.0; these are the steps between a private repository that works and a public one that strangers can use, trust and contribute to. Nothing here changes the app.

## Before flipping the switch

- [ ] Push the release tags that are still local: `v0.1.0` (fb9b62a), `v0.2.0` (3b387b3), `v0.3.0` (the 3.8 merge commit). Create a GitHub release for `v0.3.0` from its CHANGELOG section.
- [ ] Deploy is live and checked at https://curve-digitizer.openengtools.com (docs/DEPLOY.md): the home screen loads, a sample opens, "Ready offline" appears on a fresh browser profile.
- [ ] Run the open manual targets and record them in CHANGELOG.md: U1 (two first-time users, PDF to CSV in under 3 minutes), the U2 keyboard-only walkthrough, and the A8 spot check of the VBA (Excel) and MATLAB/Octave code on one fit of each model.
- [ ] Settle the open decision on whether Firefox and WebKit e2e jobs block merges, and set branch protection on `main` to match (required checks, no force-push, linear history).
- [ ] Secret scan of the full history (GitHub secret scanning turns on when the repository goes public; also run it once before). There should be nothing: the project uses no secrets.
- [ ] Check that every file in the history can be published: samples are synthetic, the PDF fixtures are generated by `scripts/gen-pdf-fixtures.py`, and nothing came from a copyrighted document.
- [ ] Licence: `LICENSE` is MIT with the right holder and year; dependency licences are recorded (ADR 24 lists the build-only MPL and CC-BY ones).

## README polish

- [ ] A screenshot or short GIF at the top: a PDF crop being traced, then the fit and code panel. Store images under `docs/images/` and keep each under 300 kB.
- [ ] A "Try it" link to the live site above the fold, and one line on privacy (nothing leaves the browser).
- [ ] Replace agent-oriented wording that reads oddly to newcomers; keep the link to CLAUDE.md for contributors.
- [ ] A short "How it compares" paragraph without naming other products' internals: PDF-first, traceable values, offline.
- [ ] Browser note: works best in Chrome and Edge.

## Issues, labels and discussions

- [ ] Labels: the ones in `.github/labels.json` (M0–M3, decision, bug, enhancement) are synced by the labels workflow; add `good first issue`, `help wanted`, `docs` and `rev-1` there so they stay in code.
- [ ] Issue templates under `.github/ISSUE_TEMPLATE/`: bug report (matching what the in-app reporter prefills: version, browser, step, error), feature request pointing at docs/ROADMAP.md, and a `config.yml` linking Discussions for questions.
- [ ] Turn on GitHub Discussions with categories Q&A, Ideas (rev 1 candidates) and Show and tell (charts people digitized).
- [ ] Open one issue per rev 1 roadmap candidate, labelled `enhancement` and `rev-1`, so people can vote with reactions.
- [ ] Triage the open issues (for example #40, saving the reference overlay) and close or label each one.

## Community files

- [ ] `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1); CONTRIBUTING.md links to it.
- [ ] `SECURITY.md`: how to report a vulnerability privately (GitHub private vulnerability reporting), and the scope (the app is static; no server).
- [ ] Repository description, website link and topics (`digitizer`, `engineering`, `pdf`, `curve-fitting`, `pwa`, `offline-first`).
- [ ] Social preview image (1280 × 640).

## After it is public

- [ ] Post on openengtools.com and wherever engineers who digitize charts will see it.
- [ ] Watch the first week of issues for setup problems in CONTRIBUTING.md and SETUP.md.
